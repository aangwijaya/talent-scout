05 Agent security

What our agents can't do,
by design

The harness and GitHub enforce these limits. Asking the agents nicely is not the safeguard.

No production credentialsAgents run with an allowlisted env, a separate database, a fake LLM and email to logs only.
No push, no mergeEach agent has its own GitHub token that can read and write issues only. GitHub refuses their pushes.
Fenced pathsA node may change only the files its issue lists. The gate rejects anything outside the fence.
Contracts need a humanChanges to the API, events or PRD start as a contract-change issue that a person approves.
Tests that biteTests must be seen red first, then a verifier sabotages the code to prove they catch breakage.
Two agents check each otherThe agent that didn't write the code reviews it. Findings are checked against the code before anyone merges.
A person always holds the last key: secrets, production data, live model runs and every merge.

06 AI safety in the product

An applicant can't talk
the AI into a 5

Untrusted data blocksCVs, answers and job text reach the models wrapped as data. Forged block delimiters are removed.
Scores need verbatim quotesCode checks every evidence quote against the real answers. A missing quote triggers a retry or manual review.
Paste detection is advisoryTyping and paste signals warn the recruiter. They never reject anyone or change a score.
Hard limits in code15 minutes, 15 questions, one question per turn and 120 words per reply, all enforced by code.
Tokens done rightSession links are one-time and stored as SHA-256 hashes. The recruiter token lives in an httpOnly cookie.
Locked-down dataRow-level security is on every table with no public policies. CVs sit in a private bucket.
Two systems, one principle: AI does the work, code checks it, and a person decides.
